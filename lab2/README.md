# DEFENSE — Завдання 2: Вимоги та Use Cases

**Намір і критерії:**
Сформувати однозначні вимоги (EARS) та сценарії використання (User Stories, Gherkin) для ігрового маркетплейсу, забезпечити їх трасування та візуалізувати через Use Case діаграму з урахуванням зовнішніх систем.

**Топ-3 розбіжності (аудит початкової генерації) + коміт-виправлення:**
Коміт-виправлення: [`41d8c3d`](https://github.com/Rostislav77-hub/KPI-Architecture-Labs/commit/41d8c3d)
1. **Двозначність EARS:** Початкова вимога REQ-01 містила розмите слово "process". Її було переписано з чіткою умовою перевірки балансу (`IF wallet_balance >= price`), що повністю узгоджується з атрибутом `wallet_balance` моделі даних з Лаби 1.
2. **Відсутність include/extend:** У первинній Use Case діаграмі бракувало зв'язків. Додано `<<include>>` (Купівля обов'язково включає перевірку балансу) та `<<extend>>` (Поповнення гаманця розширює Купівлю, якщо коштів недостатньо).
3. **Трасування UI-вимог:** Вимогу REQ-04 (підсвічування легендарних скінів золотим) навмисно залишено непокритою у матриці трасування з поясненням, оскільки це вимога до інтерфейсу (UI), а не бізнес-логіки Use Case.

**Ключове рішення — чому такі межі сценаріїв (System Boundaries):**
Межа системи проходить по внутрішньому гаманцю гравця. Сам процес списання реальних грошей з банківської картки винесено за межі нашої системи на зовнішнього актора `PaymentGateway`. Наш маркетплейс лише ініціює запит і чекає підтвердження для зміни `wallet_balance`. Це знімає з нас відповідальність за обробку конфіденційних платіжних даних.

**Перевірка — узгодженість із моделлю даних (Лаба 1):**
Актори та сценарії жорстко прив'язані до ER-моделі з першого завдання. Сценарій купівлі оперує сутностями `Player` та `InventoryItem`, а бізнес-правила (REQ-01) спираються на існуючий атрибут `wallet_balance`.
