# DEFENSE — Завдання 2: Вимоги та Use Cases

**Намір і критерії:**
Сформувати однозначні функціональні (EARS) та нефункціональні (NFR) вимоги, а також покрити ключову фічу декількома сценаріями (User Stories, Gherkin), забезпечивши їх трасування та візуалізацію через Use Case діаграму з урахуванням зовнішніх систем.

**Топ-3 розбіжності (аудит початкової генерації) + коміт-виправлення:**
Коміт-виправлення: [`41d8c3d`](https://github.com/Rostislav77-hub/KPI-Architecture-Labs/commit/41d8c3d) та наступні коміти з деталізацією NFR.
1. **Двозначність EARS:** Початкова вимога REQ-01 містила розмите слово "process". Її було переписано з чіткою умовою перевірки балансу (`IF wallet_balance >= price`), що повністю узгоджується з атрибутом `wallet_balance` моделі даних з Лаби 1.
2. **Відсутність include/extend:** У первинній Use Case діаграмі бракувало зв'язків. Додано `<<include>>` (Купівля обов'язково включає перевірку балансу) та `<<extend>>` (Поповнення гаманця розширює Купівлю, якщо коштів недостатньо).
3. **Упередженість до Happy Path (відсутність негативних сценаріїв та NFR):** ШІ згенерував лише базовий успішний сценарій. Було вручну додано негативні Gherkin-сценарії (нестача коштів, конкурентний доступ до предмета) та нефункціональні вимоги (NFR щодо ACID-атомарності транзакцій).

**Ключове рішення — чому такі межі сценаріїв (System Boundaries):**
Межа системи проходить по внутрішньому гаманцю гравця. Сам процес списання реальних грошей з банківської картки винесено за межі нашої системи на зовнішнього актора `PaymentGateway`. Наш маркетплейс лише ініціює запит і чекає підтвердження для зміни `wallet_balance`. Це знімає з нас відповідальність за обробку конфіденційних платіжних даних. Також прийнято рішення забезпечити строгу ACID-атомарність (NFR-02) для захисту від подвійної купівлі одного предмета.

**Перевірка — узгодженість із моделлю даних (Лаба 1):**
Актори та сценарії жорстко прив'язані до ER-моделі з першого завдання. Сценарій купівлі оперує сутностями `Player` та `InventoryItem`, а бізнес-правила (REQ-01) спираються на існуючий атрибут `wallet_balance`.
