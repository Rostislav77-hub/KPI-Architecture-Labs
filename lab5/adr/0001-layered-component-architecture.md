# ADR 0001: Вибір декомпозиції за горизонтальними шарами (Варіант A) та правил портів і контрактів

- **Status:** Accepted
- **Date:** 2026-11-16

## Context
Необхідно побудувати компонентну діаграму системи `In-Game Marketplace System`, яка об'єднує всі попередні артефакти (ER-модель із Лаби 1, вимоги `UC-01` із Лаби 2, Sequence із Лаби 3 та Activity із Лаби 4) і визначає межу системи, порти серверного процесу, публічні контракти (`lollipop/socket`) та внутрішні залежності.

## Decision Drivers
- Консистентність архітектурної декомпозиції та стабільний напрям рівня абстракції (`Presentation → API → Services → Data access → DB`, п. 11.12–11.13).
- Чітке розмежування портів на межі процесу, змінних контрактів (`lollipop/socket`) і прямих залежностей (`..>`) усередині бекенду без інформаційного шуму («Lollipop на кожному класі», п. 11.4, 11.7, 11.16).
- Відповідність єдиній реляційній ER-моделі з Лаби 1 (`Player`, `InventoryItem`, `MarketTransaction`), де транзакція купівлі атомарно оновлює всі три таблиці (`NFR-02`).

## Considered Options
1. **Варіант A — Горизонтальні шари (`API controllers → Services → Data access repositories`) всередині єдиного процесу `Marketplace Backend` із портами на межі та спільною схемою `Marketplace DB`.**
   - *Плюси:* Пряма відповідність спільній ER-схемі Лаби 1; `TransactionService` координує `InventoryService` і `WalletService` в межах одного процесу та спільного SQL-порту (`NFR-02`); відсутність зайвих `lollipop`-інтерфейсів між внутрішніми класами; єдиний `Router` для `REST /api` та окремий вхід `webhook in` для `PaymentWebhookController`.
   - *Мінуси:* Відсутність жорсткої ізоляції схем БД між окремими бізнес-фічами.
2. **Варіант B — Вертикальні зрізи (`Feature Modules`: окремі пакети `Inventory`, `Wallet`, `Checkout`, `Auth` із власними схемами БД та `SQL out` портами на кожен модуль).**
   - *Плюси:* Висока ізоляція доменних модулів у великих системах із десятками фіч.
   - *Мінуси:* Штучне дроблення компактної ER-моделі Лаби 1 (3 таблиці) на окремі схеми БД; ускладнення атомарної транзакції купівлі (`fork/join` із Лаби 4) між різними модулями.
3. **Низькорівнева діаграма з `lollipop`-інтерфейсами на кожному внутрішньому класі (`ITransactionService`, `IInventoryRepository` тощо) без виділення портів процесу.**
   - *Плюси:* Формальна імітація DI-контейнера у коді.
   - *Мінуси:* Типова помилка моделювання (п. 11.16): перевантажує діаграму шумом там, де заміна постачальника не передбачена, і розмиває межу між внутрішніми викликами в пам'яті та мережевими викликами за межі програми.

## Decision
Обрано **Варіант A (горизонтальні шари)**:
- `Marketplace Backend` моделюється як один процес із 7 портами на межі (`HTTP in`, `webhook in`, `WS out`, `OIDC out`, `PSP out`, `email/push out`, `SQL out`).
- Контракти `lollipop/socket` використовуються виключно поза межею процесу (для зв'язку з `Marketplace Web UI`, зовнішніми системами `<<external>>` та процесом `Marketplace DB`).
- Усередині `Marketplace Backend` між `Router`, контролерами, сервісами та репозиторіями використовуються прямі пунктирні залежності (`..>`).

## Consequences
- **Позитивні:** Діаграма легко сканується зверху вниз, точно відображає мережеві межі процесу через порти та не містить зайвих внутрішніх `lollipop`-кружечків.
- **Негативні / компроміси:** Оскільки схема БД спільна для всіх репозиторіїв, контроль за тим, щоб зміни таблиць не ламали суміжні сервіси, покладається на рівень репозиторіїв.
